# TheraSim Update and Recovery Specification

**Document ID:** THERASIM-UPDATE-RECOVERY-001
**Version:** 0.1
**Status:** Architecture Draft; manual read-only metadata lookup is implemented,
but this full update, signing, and recovery design is not
**Target Platform:** Windows x64
**Update Source:** GitHub Releases
**Last Updated:** 2026-11-16

---

## 1. Purpose

This document defines the application update, release verification, database backup, and recovery architecture for TheraSim.

The objective is to allow end users to check for, download, and install official TheraSim updates directly from the desktop application.

Users must not need to open GitHub, use Git, download source code, or execute terminal commands to update the application.

Application updates must preserve all persistent user data.

## 2. Update Scope

The initial update system covers:

- Desktop application updates.
- Frontend application updates.
- Backend executable updates.
- Bundled application resource updates.
- Compatible database schema migrations.

The initial update system does not automatically update:

- Ollama.
- LM Studio.
- External language models.
- User exports.
- User-managed model files.
- Arbitrary files outside the application installation directory.

Updates to educational content, case definitions, and evaluation rubrics will use a separate content versioning mechanism in a later implementation stage.

## 3. Update Distribution Source

Official application releases will be distributed through the project's GitHub Releases.

The application must use versioned release artifacts rather than retrieving and executing source code from the main development branch.

The intended update endpoint for the Stable channel is:

https://github.com/OWNER/REPO/releases/latest/download/latest.json

The actual repository owner and name must be configured before the first public release.

The application must remain functional when GitHub is unavailable.

## 4. Versioning

Application releases must follow Semantic Versioning.

Version format:

MAJOR.MINOR.PATCH

Examples:

- 0.1.0
- 0.2.0
- 1.0.0
- 1.1.0

The version displayed in the application must match the version embedded in the installed release.

Pre-release versions may use identifiers such as beta or rc.

Stable and Beta update channels must be independently configurable.

The initial public update channel is Stable.

## 5. Tauri Updater

The proposed update implementation uses the official Tauri 2 Updater plugin.

The updater configuration must include:

- Update artifact generation.
- Public signing key.
- HTTPS update endpoint.
- Windows installation mode.
- Explicit update channel configuration where required.

The Tauri bundler must generate signed updater artifacts.

The Windows update installation mode is initially planned as passive, displaying installation progress without requiring unnecessary user interaction.

The final configuration must be verified against the Tauri version selected for the release.

## 6. Static Update Manifest

The Stable update endpoint will provide a versioned JSON manifest named:

latest.json

The manifest must follow the static manifest contract supported by Tauri Updater.

Required information includes:

- version
- platforms
- platforms.windows-x86_64.url
- platforms.windows-x86_64.signature

Optional information includes:

- notes
- pub_date

The Windows platform entry must identify the official update artifact URL and contain the actual signature text generated for that artifact.

A URL pointing to a signature file is not a substitute for the signature content required by the manifest.

The manifest must be generated by the release pipeline rather than manually maintained.

## 7. Update Signing

Tauri update artifacts must be cryptographically signed.

Two signing components are required:

### Public Key

The public key is embedded in the application updater configuration.

It is not a secret and may be distributed with the application.

### Private Key

The private signing key is used only in the trusted release environment.

It must:

- Never be committed to Git.
- Never be included in application resources.
- Never be included in the installer.
- Never be sent to end users.
- Never appear in build logs.
- Be protected with an appropriate password and secure backup.

GitHub Actions secrets or an equivalent protected release environment will provide signing credentials during release builds.

Losing the private signing key may prevent future updates from being accepted by existing installations.

An offline protected backup of the signing key is mandatory.

## 8. Additional Release Integrity

The release pipeline should also generate SHA-256 checksums for release artifacts.

Checksums are supplementary release verification metadata.

They do not replace Tauri's cryptographic updater signature.

Release artifacts must be associated with:

- Application version.
- Git commit identifier.
- Release tag.
- Target operating system.
- Target architecture.
- Build timestamp.
- Artifact checksum.
- Updater signature.

## 9. Update User Experience

The application will provide an Updates section in its settings or application information area.

The interface should display:

- Installed version.
- Latest available version.
- Update channel.
- Last update check.
- Release notes.
- Update availability.
- Download and installation status.

The user must be able to manually check for updates.

Automatic update checks may also be performed periodically without blocking normal application startup.

The application must never require a GitHub account for ordinary public release downloads.

The application must not force an update merely because GitHub is temporarily unavailable.

## 10. Update Workflow

The expected update lifecycle is:

1. The user requests an update check or an automatic check is triggered.
2. The application requests the configured update manifest.
3. The updater checks the published version.
4. The application displays available release information.
5. The user approves installation according to update policy.
6. The official artifact is downloaded.
7. The updater verifies the cryptographic signature.
8. The application prepares for shutdown.
9. The installer applies the update.
10. The application restarts.
11. The new application version is verified.
12. A successful update is recorded.

An invalid signature, unsupported target, incomplete package, or failed download must prevent installation.

## 11. Update Safety

Application updates must not directly modify persistent user data unless an explicitly versioned migration requires it.

Updates must not:

- Delete user databases.
- Replace user configuration with defaults.
- Remove user exports.
- Remove user-managed model files.
- Reset provider settings.
- Execute arbitrary scripts from the development branch.
- Disable existing application security boundaries.

Application files must remain separate from user data.

## 12. Database Backup Before Migration

A database backup is required before applying update-related migrations.

The backup process must treat the operational and restricted databases as one coordinated recovery unit.

The backup procedure must:

1. Prevent conflicting database writes.
2. Reach a safe persistence boundary.
3. Handle SQLite WAL state correctly.
4. Use SQLite's supported backup mechanism where applicable.
5. Verify both backup files.
6. Record database schema versions.
7. Record application version.
8. Write a recovery manifest.
9. Mark the backup as valid only after verification.

A partially completed backup must not be treated as a valid recovery point.

The two databases retain their independent migration histories.

## 13. Backup Storage

Proposed backup location:

%LOCALAPPDATA%\TheraSim\backups\

A backup set may contain:

- therasim.db backup.
- case_vault.db backup.
- Backup manifest.
- Application version metadata.
- Database schema version metadata.
- Creation timestamp.
- Verification status.

The backup manager should maintain a configurable retention policy.

The initial retention target is three successful pre-migration backup sets.

Backup cleanup must never remove the only known valid recovery point.

## 14. Database Migration Workflow

After a verified pre-update backup:

1. The application prepares the migration.
2. The Backend is stopped or brought to a safe migration state.
3. Database schema versions are inspected.
4. Operational migrations are applied.
5. Restricted migrations are applied independently.
6. Database integrity is checked.
7. Foreign key constraints are verified.
8. Application compatibility is checked.
9. The update is marked successful only after all required checks pass.

The update process must not assume that two independent SQLite databases can participate in one atomic database transaction.

The recovery manager must coordinate both databases explicitly.

## 15. Recovery Strategy

If an application update or database migration fails:

- The application must report the failure.
- The recovery manifest must identify the last valid backup set.
- The operational and restricted databases must be restored as a coordinated pair when required.
- Database integrity must be verified after restoration.
- The previous compatible application release must remain available for recovery.
- The application must not silently create empty replacement databases.

The implementation must not assume that Tauri's standard updater automatically rolls back every failed installation.

Automatic application binary rollback is a separate capability that must be designed and tested explicitly.

The initial release must provide a documented and user-accessible recovery path.

## 16. Update Compatibility

Every application release must declare its supported database schema range.

A release must not start against an unsupported schema version.

Database migrations must be designed with explicit upgrade compatibility.

Before releasing an update that changes persisted data, the development process must review:

- Migration compatibility.
- Backup availability.
- Failure recovery.
- Application version compatibility.
- Whether the previous application release can operate with the migrated schema.

Destructive database changes must not be introduced without an explicit migration and recovery plan.

## 17. Release Pipeline

The intended GitHub Actions release workflow is:

1. Create a Semantic Versioning Git tag.
2. Run backend tests.
3. Run frontend lint checks.
4. Run frontend production build.
5. Package the backend executable.
6. Build the Tauri desktop application.
7. Generate Windows installer and updater artifacts.
8. Generate cryptographic signatures.
9. Generate the latest.json manifest.
10. Generate artifact checksums.
11. Publish the signed release artifacts.
12. Publish the update manifest.
13. Verify the published update endpoint.

The release must be traceable to a specific source commit.

Signing credentials must be available only to authorized release jobs.

## 18. GitHub Release Assets

The Stable Windows release is expected to publish:

- TheraSim-Setup.exe: Standard Windows installer.
- TheraSim-Setup.nsis.zip: Tauri Windows updater bundle.
- TheraSim-Setup.nsis.zip.sig: Cryptographic signature of the updater bundle.
- latest.json: Static update manifest containing the generated signature text and updater artifact URL.
- SHA256SUMS.txt: Checksums for published release artifacts.
- Release notes.

The standard installer and updater bundle are distinct artifacts in the Tauri NSIS distribution process.

The manifest must reference the updater bundle, not assume that the ordinary installer executable is the updater payload.

The exact artifact names must be taken from the actual Tauri build output.

The signature content must be copied from the generated signature artifact by the release pipeline. It must never be manually invented or modified.
## 19. Failure Scenarios

The implementation must test at least:

1. GitHub is unavailable.
2. Update manifest is unavailable.
3. Update manifest is malformed.
4. A release targets a different architecture.
5. The update package download is interrupted.
6. The update signature is invalid.
7. Disk space is insufficient.
8. The installer fails.
9. The application cannot restart.
10. A database migration fails.
11. The operational database backup is invalid.
12. The restricted database backup is invalid.
13. Database restoration fails.
14. The installed application encounters an unsupported schema.

In all cases, user data must be protected from silent deletion or replacement.

## 20. Security Constraints

The update system must preserve these rules:

- HTTPS is mandatory in production.
- Cryptographic signature verification is mandatory.
- The updater public key is embedded in the application.
- The private signing key is never distributed.
- GitHub source branches are not executable update packages.
- Release artifacts must be versioned.
- User data must remain outside the application installation directory.
- The application must not expose secrets in logs.
- Updates must not bypass persistence security boundaries.

## 21. Acceptance Criteria

The update and recovery implementation will not be considered complete until:

1. The application can discover a published Stable release.
2. Release notes and version information are displayed.
3. A valid signed update can be downloaded.
4. An invalid signature is rejected.
5. GitHub unavailability does not block application startup.
6. User settings survive application updates.
7. Both databases survive ordinary application updates.
8. Database backups are verified before migrations.
9. Failed migrations trigger the documented recovery process.
10. Existing user exports and model files remain intact.
11. The application can verify its installed version after restart.
12. Release artifacts can be traced to their source commit.

## 22. Implementation Status

This document records the intended update and recovery architecture.

For the current release, manual update checks may report stable GitHub release
metadata and source-checkout status. They do not download or install a package,
do not invoke Git to change files, and do not perform database migrations.
Portable users must download and verify an official package manually. The
Tauri, signature, manifest, pre-migration backup, rollback, and coordinated
recovery components below remain planned.

The following components are planned and not yet implemented:

- Tauri Updater integration.
- GitHub release manifest generation.
- Release signing.
- Update settings interface.
- Update download and installation flow.
- Pre-migration backup manager.
- Coordinated database recovery.
- Update compatibility checks.
- GitHub Actions release pipeline.
- Update and recovery integration tests.

Implementation must proceed after architecture review and completion of the relevant contracts.
