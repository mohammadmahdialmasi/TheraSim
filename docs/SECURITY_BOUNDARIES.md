# TheraSim — Security Boundaries and Agent Isolation

**Document Version:** 0.1
**Project Status:** Research Prototype / Pre-MVP
**Last Updated:** 2026-11-14

---

## 1. Purpose

This document defines the security architecture, access boundaries, and information protection requirements of TheraSim.

The system uses multiple language-model agents that operate with different responsibilities and access requirements.

The primary security objectives are:

- Prevent unauthorized disclosure of restricted synthetic case information.
- Enforce least-privilege access between system components.
- Protect internal prompts and agent instructions.
- Prevent untrusted conversational content from overriding system instructions.
- Validate all model-generated outputs before they modify persistent data.
- Protect session transcripts, memory records, and evaluation reports.
- Maintain an auditable record of security-relevant operations.
- Preserve the educational and non-clinical boundaries of the platform.

The initial system is designed for local, single-user operation and synthetic cases only.

This document describes intended security controls. The presence of a control in this specification does not mean it has already been implemented or independently validated.

---

## 2. Security Principles

The security architecture follows these principles.

### 2.1 Least Privilege

Every component receives only the data and capabilities required for its responsibilities.

No agent should receive unrestricted access to the application database, filesystem, or other agents' internal context.

### 2.2 Defense in Depth

Security must not depend on a single mechanism or prompt instruction.

Multiple layers should enforce the same critical boundary where appropriate.

Examples:

- Restricted repository interfaces.
- Explicitly constructed agent inputs.
- Schema validation.
- Output validation.
- API authorization.
- Database separation.
- Audit logging.

### 2.3 Zero Trust Between Components

An internal component must not automatically trust another component's output.

Every request and response must be validated according to its contract.

This includes outputs generated by the Patient Agent, Evaluator Agent, event extraction layer, and memory processor.

### 2.4 Data Minimization

Only the minimum information necessary for a specific operation should be transferred.

Unnecessary personal history, hidden case details, and unrelated memory entries must not be included in an agent context.

### 2.5 Explicit Information Classification

Data must have an explicit information classification.

The classification determines which components may access or process it.

### 2.6 Fail-Safe Defaults

When access authorization or validation cannot be established, the system must deny access or reject the operation by default.

An unavailable security service must not result in unrestricted access.

## 3. Threat Model

The initial threat model identifies the main assets, potential threats, and security boundaries.

### 3.1 Protected Assets

The following assets require protection:

1. Restricted synthetic case formulation.
2. Undisclosed synthetic client history.
3. Patient Agent instructions.
4. Evaluator instructions and rubric configuration.
5. Session transcripts.
6. Longitudinal memory.
7. Clinical state snapshots.
8. Evaluation reports.
9. Database files and backups.
10. Model configuration and application secrets.
11. Audit records.

### 3.2 Potential Threats

The system should account for:

- Prompt injection through therapist messages.
- Malicious or misleading content inside simulated conversations.
- Attempts to retrieve hidden case information through the API.
- Accidental transfer of restricted data between agents.
- Unauthorized access to local database files.
- Exposure of sensitive information through application logs.
- Malformed or adversarial model outputs.
- Duplicate or unauthorized state modifications.
- Compromised model files or software dependencies.
- Accidental exposure through backups or exported files.
- Unauthorized access through an incorrectly configured network interface.

### 3.3 Threat Actors

Initial threat scenarios include:

- An ordinary user unintentionally submitting unsafe or restricted content.
- A user deliberately attempting to reveal hidden case information.
- Malicious instructions embedded within conversational text.
- A compromised or manipulated model output.
- An unauthorized process operating on the same computer.
- A malicious software dependency or modified model artifact.

### 3.4 Security Scope

The initial MVP does not attempt to provide complete protection against:

- A computer with a compromised operating system.
- An administrator with unrestricted access to the machine.
- Physical access to an unlocked device.
- Advanced malware operating with the same privileges as the application.
- A malicious local user who already has unrestricted access to application files.

These limitations must be documented rather than hidden behind the local-first design claim.

## 4. Information Classification

Every important data object must belong to one of the following information classes.

### 4.1 Public Simulation Information

Examples:

- Approved case names.
- Case identifiers.
- Therapeutic modality.
- General simulation descriptions.
- Published documentation.

Access:

- Authorized frontend.
- Orchestrator.
- Relevant internal components.

### 4.2 Therapist-Visible Information

Examples:

- Approved client introduction.
- Information disclosed during the simulated interaction.
- Therapist-submitted messages.
- Patient responses visible in the session.
- Completed evaluation reports.

Access:

- Therapist Interface.
- Orchestrator.
- Components explicitly authorized to process the relevant information.

### 4.3 Restricted Case Information

Examples:

- Complete clinical formulation.
- Undisclosed personal history.
- Maintaining-factor hypotheses.
- Hidden behavioral patterns.
- Internal disclosure strategy.
- Restricted case-specific instructions.

Access:

- Patient Context component.
- Patient Agent through an explicitly constructed context object.

The Evaluator Agent, Therapist Interface, and ordinary API endpoints must not access this information.

### 4.4 Internal Operational Information

Examples:

- Agent prompts.
- Model configuration.
- Event extraction instructions.
- Transition rules.
- Internal diagnostic logs.
- Repository configuration.

Access:

- Only the components that require the relevant operational information.

### 4.5 Security-Critical Information

Examples:

- Application secrets.
- Encryption keys.
- Database access credentials.
- Authentication tokens.
- Sensitive backup information.

Access:

- Authorized application infrastructure only.

Security-critical information must never be inserted into ordinary agent prompts or conversation transcripts.

## 5. Agent Access Boundaries

### 5.1 Patient Agent

The Patient Agent must receive:

- Minimum required synthetic identity information.
- Relevant restricted case context.
- Current structured simulation state.
- Relevant longitudinal memory.
- Current session context.
- Latest therapist message.
- Disclosure constraints applicable to the current interaction.

The Patient Agent must not receive:

- Database credentials.
- Unrestricted filesystem access.
- Arbitrary operating-system commands.
- External network access.
- Evaluator internal instructions.
- Unrelated cases.
- Application secrets.

The Patient Agent may use restricted case information to maintain behavioral consistency.

However, possession of hidden information does not authorize automatic disclosure of that information to the therapist.

### 5.2 Evaluator Agent

The Evaluator Agent must receive:

- Finalized session transcript.
- Applicable evaluation rubric.
- Authorized therapist-visible session context.
- Relevant evaluation instructions.
- Transcript identifiers and evidence references.

The Evaluator Agent must not receive:

- Restricted clinical formulation.
- Undisclosed personal history.
- Hidden Patient Agent instructions.
- Private Patient Agent context.
- Future planned responses.
- Unavailable internal state variables.
- Database credentials or unrestricted repository access.

The Evaluator must assess observable therapist behavior rather than compare the therapist's performance against information that was inaccessible during the interaction.

### 5.3 Clinical State Engine

The Clinical State Engine may receive:

- Current structured state.
- Candidate events.
- Validated transcript evidence.
- Versioned transition rules.
- Authorized simulation metadata.

It must not receive unrestricted access to restricted case storage.

It must not accept direct state modification commands from a language model without validation.

### 5.4 Memory Service

The Memory Service may process:

- Authorized session transcripts.
- Accepted event records.
- Explicitly classified memory candidates.
- Relevant historical memory.

It must preserve distinctions between:

- Disclosed facts.
- System-generated summaries.
- Therapist hypotheses.
- Reported outcomes.
- Structured observations.

It must not silently convert a hypothesis into an established fact.

The initial unauthenticated version recorded `unverified_local_caller`.
Migration 014 supersedes that baseline: review operations now require an
authenticated local session and record the stable `local-reviewer` account ID.

### 5.5 Orchestrator

The Orchestrator coordinates system operations.

It should use explicitly defined service interfaces rather than unrestricted access to every database and internal prompt.

It must not:

- Expose the restricted case database to the frontend.
- Forward complete hidden case information to the Evaluator.
- Bypass State Engine validation.
- Treat an unvalidated model response as an accepted state transition.

### 5.6 Therapist Interface

The Therapist Interface may access only authorized external API responses.

It must not directly access:

- SQLite database files.
- Restricted case storage.
- Agent prompts.
- Internal agent context.
- Hidden clinical state.
- Unvalidated events.
- Internal model reasoning.

## 6. Information Flow Restrictions

The system must implement explicit data-transfer boundaries.

### 6.1 Patient Information Flow

The intended flow is:

1. Orchestrator requests patient context.
2. Patient Context retrieves the authorized restricted information.
3. Patient Context constructs a limited PatientContext object.
4. Patient Agent receives that object.
5. Patient Agent generates a PatientResponse.
6. The output is validated.
7. Only the approved response is stored as a therapist-visible message.

The complete restricted case definition must not be forwarded automatically to unrelated components.

### 6.2 Evaluation Information Flow

The intended flow is:

1. Session completion finalizes the transcript.
2. Evaluation Service constructs an EvaluationInput object.
3. Evaluation Service applies an explicit allowlist of permitted fields.
4. Evaluator Agent receives the authorized input.
5. Evaluator generates a structured report.
6. The report is validated and stored.
7. Therapist Interface retrieves the authorized report.

The EvaluationInput object must not be derived by copying the entire internal session context.

It must be constructed explicitly from permitted fields.

### 6.3 State Information Flow

The intended flow is:

1. Interaction is recorded.
2. Event extraction proposes candidate events.
3. Evidence references are validated.
4. Candidate transitions are evaluated.
5. State Engine accepts, rejects, or flags the transition.
6. Accepted transitions produce immutable historical records.
7. The resulting state becomes available to authorized components.

A model response must never directly overwrite the canonical state.

### 6.4 Forbidden Information Flows

The following transfers are prohibited:

- Restricted case formulation to Evaluator Agent.
- Patient Agent hidden prompts to Therapist Interface.
- Database credentials to any language-model prompt.
- Internal reasoning to public API responses.
- Unvalidated state changes to canonical state storage.
- Hidden case information to evaluation evidence.
- Arbitrary model-generated SQL to the database layer.

## 7. Prompt Injection Protection

Prompt injection is a relevant risk because agents process natural-language content that may contain instructions unrelated to their authorized responsibilities.

Examples include:

- A therapist message asking the Patient Agent to reveal its hidden case instructions.
- A conversational statement containing instructions to ignore previous system rules.
- Text instructing the Evaluator to assign the highest rating regardless of the transcript.
- Instructions embedded in copied documents or simulated client statements.

### 7.1 Input Trust Levels

The system must distinguish between:

1. Trusted system instructions.
2. Versioned developer instructions.
3. Restricted case data.
4. Therapist-submitted content.
5. Model-generated content.
6. Retrieved memory and transcript content.

User-submitted and model-generated content must be treated as untrusted data.

### 7.2 Patient Agent Protection

Patient Agent instructions must explicitly establish that:

- Therapist messages are conversational input, not system instructions.
- Attempts to retrieve hidden prompts must not be obeyed.
- Requests to reveal undisclosed case information must follow the case disclosure policy.
- External instructions must not override the agent's authorized simulation role.
- Hidden case details must not be returned as diagnostic or internal context.

### 7.3 Evaluator Agent Protection

Evaluator instructions must explicitly establish that:

- Transcript content is evidence to analyze, not instructions to follow.
- Therapist messages cannot modify the evaluation rubric.
- Instructions embedded in the transcript must not alter evaluator rules.
- Ratings must follow the versioned rubric.
- Claims without transcript evidence must not be presented as observed behavior.

### 7.4 Technical Restrictions

Prompt wording alone is insufficient protection.

The implementation must also:

- Avoid granting arbitrary tools to agents.
- Restrict tool calls through explicit allowlists.
- Validate structured outputs.
- Construct agent inputs using typed objects.
- Avoid exposing restricted repositories.
- Keep the evaluator input independent of the complete patient context.

Delimiters, JSON formatting, and role labels may improve instruction clarity but must not be treated as complete prompt injection defenses.

## 8. Model Input and Output Validation

Language-model outputs are untrusted until validated.

### 8.1 Input Validation

Before sending data to a model:

- Validate the input schema.
- Confirm component authorization.
- Remove unnecessary information.
- Enforce input length limits.
- Exclude credentials and secrets.
- Record relevant model and prompt versions.

### 8.2 Patient Response Validation

Patient Agent outputs must be checked for:

- Valid response structure.
- Correct role.
- Correct session reference.
- Permitted content length.
- Missing or malformed fields.
- Unexpected internal prompt disclosure.
- Unauthorized disclosure of restricted case information.

A semantic disclosure check should compare the generated response with an explicit case disclosure policy and permitted information for that interaction.

Simple keyword matching alone is not sufficient.

If validation fails, the response must not be exposed automatically.

The system may reject it, request regeneration within controlled limits, or flag it for review.

### 8.3 Evaluator Output Validation

Evaluator outputs must be checked for:

- Valid rubric identifiers.
- Permitted rating values.
- Valid competency identifiers.
- Existing transcript message references.
- Evidence consistency.
- Missing required fields.
- Unauthorized claims of clinical certification or validated competence.

An invalid evaluation must not be stored as a completed report.

### 8.4 State Output Validation

Candidate transitions must be checked by deterministic application logic.

Validation must include:

- Variable allowlist.
- Numerical range.
- Evidence existence.
- Session consistency.
- Idempotency.
- Transition rule compatibility.

The language model must not have direct write privileges over canonical clinical state records.

## 9. Tool and Resource Restrictions

Language-model agents must not receive unrestricted execution capabilities.

### 9.1 Prohibited Capabilities

Agents must not be granted:

- Arbitrary shell access.
- Arbitrary PowerShell execution.
- Arbitrary filesystem read or write.
- Unrestricted database queries.
- Arbitrary SQL execution.
- Unrestricted network access.
- Access to application secrets.
- Permission to install packages.
- Permission to modify system configuration.

### 9.2 Allowed Capabilities

If an agent requires an operation, it must use a narrowly defined internal tool.

Examples:

- Retrieve authorized patient context.
- Retrieve relevant longitudinal memory.
- Submit candidate events.
- Request transition validation.
- Submit a structured evaluation result.

Each tool must define:

- Authorized caller.
- Input schema.
- Output schema.
- Permitted operations.
- Error behavior.
- Audit requirements.

No agent should be able to expand its own permissions.

## 10. Local Deployment Security

The initial deployment targets a local Windows environment.

### 10.1 Network Configuration

Initial requirements:

- FastAPI binds to `127.0.0.1` by default.
- External network access is disabled unless explicitly required.
- Ollama uses a local endpoint.
- Frontend communication is restricted to the local backend.
- No public cloud API is mandatory.
- Network exposure must require an explicit configuration change.

Local execution must not be described as complete security protection.

### 10.2 File System Protection

The implementation should:

- Keep database files outside publicly served frontend directories.
- Restrict access to application data directories.
- Avoid storing secrets in source-controlled files.
- Protect backup directories.
- Avoid exposing internal logs through the web server.
- Use appropriate Windows file permissions.

The paired backup CLI writes under the current user's local application data
directory by default on Windows. The optional `backup --encrypt` format uses
AES-256-GCM and scrypt-derived keys; restore verifies authenticated ciphertext
and targets a new directory without overwriting existing data. The passphrase
is not stored and has no recovery path. Plain backups remain available, and
live SQLite database files are not encrypted at rest. Operators must protect
the live data directory with filesystem permissions and device encryption.

### 10.3 Database Protection

The application must:

- Apply restricted repository access.
- Enable SQLite foreign key enforcement.
- Use parameterized database queries.
- Validate data before insertion.
- Use transactions for multi-record operations.
- Separate restricted and operational data.
- Back up databases securely.

Encryption at rest should be evaluated before distributing the application or storing sensitive operational data.

### 10.4 Ollama Configuration

The model runtime must:

- Be accessed through the intended local interface.
- Avoid unnecessary network exposure.
- Use explicitly selected model identifiers.
- Record model versions where available.
- Avoid placing restricted data into unnecessary external model services.

Model downloads and updates should be treated as software supply-chain operations.

The current provider configuration accepts HTTP(S) base URLs only and rejects
URL user-info, query strings, and fragments. The provider catalog returns only
the URL origin. Provider credentials belong in the explicit API-key
configuration, not in the URL. This does not provide authentication,
authorization, or protection against a maliciously configured provider host.

## 11. Logging and Audit Security

Logs are required for debugging and reproducibility, but they must not become an alternative path for exposing restricted information.

### 11.1 Permitted Log Information

Examples:

- Request identifiers.
- Session identifiers.
- Component names.
- Operation types.
- Timestamps.
- Execution status.
- Error codes.
- Model identifiers.
- Prompt versions.
- Validation outcomes.

### 11.2 Restricted Log Information

The following must not be logged by default:

- Complete restricted case formulations.
- Application secrets.
- Database credentials.
- Authentication tokens.
- Hidden prompts.
- Unnecessary transcript content.
- Full model internal context.

### 11.3 Audit Requirements

Security-relevant operations must produce auditable records.

Examples:

- Restricted context retrieval.
- Agent invocation.
- Access denial.
- State transition rejection.
- Evaluation generation.
- Failed output validation.
- Database backup or restoration.
- Configuration changes.

Audit records must identify the operation and its outcome without unnecessarily duplicating sensitive content.

## 12. Privacy and Data Handling

The initial MVP is limited to synthetic cases.

It must not be marketed or configured as an environment for storing real client records.

The application should clearly inform users that they must not enter identifiable real-client information.

Because automated detection of identifying information is imperfect, the application must not claim that it can reliably prevent all accidental submission of real personal data.

### 12.1 Data Minimization

- Store only information required by the simulation.
- Do not collect unnecessary personal information from trainees.
- Avoid telemetry by default.
- Do not transmit transcripts to external services.
- Keep synthetic case data separate from user-submitted interaction records.

### 12.2 Export and Backup

Exports and backups must preserve:

- Data classification.
- Case version references.
- Transcript versions.
- Rubric versions.
- State history.
- Relevant model metadata.

Restricted case information must remain subject to access restrictions after export.

### 12.3 Deletion

The application must eventually support explicit deletion policies for local user-generated data.

Deletion operations must be auditable where appropriate.

Historical simulation records must not be silently altered when a user requests deletion of a separate record.

## 13. Safety and Clinical Boundaries

TheraSim is an educational simulation platform.

Its security and safety mechanisms must not be confused with clinical risk assessment or emergency response capabilities.

The application must:

1. Identify itself as a simulation environment.
2. Use synthetic cases in the initial MVP.
3. Avoid presenting simulated responses as real clinical advice.
4. Avoid claiming that automated safety-event detection is a validated risk assessment.
5. Preserve scenario-specific safety events accurately.
6. Use explicitly designed responses for simulated safety scenarios.
7. Avoid automatic diagnostic conclusions.
8. Avoid presenting rubric scores as professional certification.

When the system is extended to support additional therapeutic modalities, each modality must have its own reviewed safety requirements.

## 14. Security Testing Requirements

Security controls must be verified through automated tests and targeted manual assessments.

### 14.1 Access Isolation Tests

- Evaluator input contains no restricted case fields.
- Frontend API responses contain no hidden case information.
- Patient Agent receives only authorized context.
- Unauthorized repository access is rejected.
- Restricted database access is limited to the authorized component.

### 14.2 Prompt Injection Tests

Test scenarios should include:

- Requests to reveal hidden case instructions.
- Requests to disclose undisclosed personal history.
- Instructions embedded inside therapist messages.
- Instructions attempting to modify evaluator ratings.
- Malicious text embedded in retrieved memory.
- Contradictory instructions inside conversation history.

Expected result:

Agent instructions and access boundaries remain enforced, and no unauthorized information is disclosed.

### 14.3 Model Output Tests

- Invalid PatientResponse objects are rejected.
- Invalid evaluation ratings are rejected.
- Unknown competency identifiers are rejected.
- Invalid evidence references are rejected.
- Out-of-range state values are rejected.
- Duplicate state transitions are prevented.
- Unexpected model-generated tool requests are denied.

### 14.4 Data Protection Tests

- Secrets do not appear in application logs.
- Database files are outside public frontend paths.
- Backups preserve access restrictions.
- API endpoints do not reveal internal error details.
- Local network binding follows the intended configuration.

### 14.5 Failure Handling Tests

- Model execution failures do not bypass output validation.
- Repository failures do not create partially accepted state transitions.
- Access-control failures do not trigger permissive fallback behavior.
- Failed security validation does not expose restricted content.

## 15. Security Acceptance Criteria for MVP

The initial MVP should not be considered ready for release until the following requirements are satisfied:

1. Patient Agent and Evaluator Agent have separate input contracts.
2. Evaluator receives no restricted case formulation.
3. Therapist-facing endpoints expose only authorized data.
4. Restricted case retrieval uses a controlled service interface.
5. Agents have no arbitrary filesystem, shell, SQL, or network access.
6. Model outputs are validated before persistence or display.
7. State changes require deterministic validation.
8. Prompt injection test cases are included in the test suite.
9. Sensitive information is excluded from ordinary logs.
10. Database files are not publicly served.
11. Local network exposure is disabled by default.
12. The synthetic-only educational boundary is clearly communicated.

All acceptance criteria must be verified through tests or implementation inspection rather than assumed from documentation.

## 16. Implemented Local Authentication

The local installation supports one reviewer account, created once through a
loopback-only initialization endpoint. Passwords are hashed with scrypt using
a per-account random salt. API sessions use opaque bearer tokens; only token
hashes are persisted, sessions expire after eight hours, and logout revokes
the current token. All data-bearing `/api/v1` routers require authentication;
health and first-run/login endpoints are public.
Evaluation review submissions record the authenticated local user ID, and
review history is append-only. Reviewer feedback is stored in the operational
database and is protected by the same bearer authentication as evaluation
reports.

The current local security boundary does not include multi-user roles,
password reset, database encryption at rest, or transport encryption.
Encrypted backups are optional and passphrase-based. Login attempts are
persisted per hashed client address and throttled after five attempts in
15 minutes; this is a local single-user safeguard, not distributed abuse
prevention. Keep the server bound to loopback and protect the data directory
and backups with operating-system access controls. Manually exposing the API
on a network is unsupported without a separately secured network and
transport boundary.

## 17. Future Security Improvements

The following improvements may be considered after the initial MVP:

- Stronger process isolation between agents.
- Dedicated operating-system accounts for restricted services.
- Database encryption at rest.
- More advanced information-flow controls.
- Automated prompt injection evaluation.
- Model artifact integrity verification.
- Dependency and software supply-chain scanning.
- Secure multi-user authentication.
- Role-based authorization.
- Advanced audit monitoring.
- Formal threat modeling.
- Independent security review.

These improvements must be prioritized according to the deployment environment and actual threat model.

## 18. Open Design Questions

The following decisions remain unresolved:

- Should Patient Context run as a separate process?
- Should the restricted case database use an encrypted SQLite implementation?
- How should Windows ACLs be configured during installation?
- Which security tests should block a release?
- How should the application handle accidental submission of real personal information?
- What is the minimum acceptable isolation between local agents?
- How should model artifacts be verified before execution?
- How should encrypted-backup passphrases be rotated or escrowed without
  weakening their separation from the backup files?
- Which security controls are mandatory before any multi-user deployment?

These questions must be resolved before expanding beyond the initial local research prototype.

## Character profile, memory, and state boundaries

Personality profiles containing internal characterization, schema hypotheses,
and restricted guidance belong in the restricted case vault.

Run-specific events, memories, and dynamic state remain in the operational
database and must be scoped to the exact run.

The PatientContext serializer remains an explicit allowlist boundary.
Adding a character field to a Python model does not authorize exposing it
through an API, evaluator context, or frontend response.

Memory retrieval must validate run identity, message provenance, chronology,
and information class. Hypotheses and structured observations must not
silently become patient-known facts.

Two runs using the same character definition must never share evolving
memory or dynamic state.

See `CHARACTER_MODEL_SPEC.md` for the complete character data boundary.
